## 同一 incident 的 observability 根因 + 修复（事件日志淹没 CI）
- 那 770MB 日志的元凶：事件日志 `org.apache.flink.agents.EventLog` 在 `ut-java` 单测里被灌进控制台。
  机制：`ci.yml` 的 `java_tests` 设 `LOG_LEVEL=INFO` → `runtime/src/test/resources/log4j2-test.properties`
  里 root logger 从默认 OFF 被覆盖成 INFO；而 `org.apache.flink.agents.EventLog` 在测试配置里**没有独立配置**，
  于是继承 root，每产生一个事件就走 `Slf4jEventLogger.append()` 的 `EVENT_LOG.info(json)` 打控制台。
  真实集群/mini-cluster 里 Flink 设了 `log.file`，`Slf4jEventLogger.ensureLog4j2AppenderConfigured()` 会建
  专用 appender 写 `{log.file}.event-log.log`；纯 surefire 单测 JVM 无 `log.file`，该方法提前 return，
  事件日志退化回 root → 全灌控制台。
- 修复：在 `runtime/src/test/resources/log4j2-test.properties` 给 `org.apache.flink.agents.EventLog`
  配独立 FILE appender（`target/event-log.log`，pattern `%msg%n`）并设 `additivity=false`，控制台恢复精简，
  事件日志仍可查。e2e/IT 模块保持不动（其 TaskManager 有 `log.file`，仍走程序化专用 appender，行为不变）。
- 结论：本次修复只解决“日志被淹没”的 observability 问题；真实失败仍是上面那条 10ms 超时 flaky 用例，需另修测试。
- 旁证（用户指出）：ubuntu-latest 的 ut-java 用完全相同的 `LOG_LEVEL=INFO` + 无 `log.file` 配置，控制台同样被事件日志淹没，却能通过。说明事件日志洪水本身**不会**导致用例失败，纯属 observability 噪音；真实失败只来自 macos 特有的 10ms flaky 用例。切勿再把“日志爆量”误判为失败根因。

## ActionState 数据结构 + Kafka/Fluss 恢复路径（对接 orphan-state issue）
- `actionStates` 是 `Map<String, ActionState>`（`KafkaActionStateStore.java:80`），但 map 的 key 是**复合键**
  `generateKey(key, seqNum, action, event)` = `key_seqNum_<eventUUID>_<actionUUID>`
  （`ActionStateUtil.java:44-56`），不是单独的业务 key。所以「多个 key / 多个 seqNum / 多个 action」
  在 map 里是互不覆盖的多条 entry。`latestKeySeqNum`（:83）声明了但从未写入，是死字段。
- 写入顺序：`put()` 每次处理一个 action 调一次（`actionStates.put(stateKey, state)`，:139）。
  HashMap 本身无序；顺序的真正载体是 **seqNum（同一 key 内的动作顺序）** 与 **Kafka offset**
  （`ActionStateKeyPartitioner` 把同一业务 key 固定路由到同一 partition，故同一 key 在 partition 内严格有序，跨 key 不保证全局顺序）。
  `get()`（:151-194）查不到或检测到 divergence（同 `key_seqNum_` 前缀 >1 条）时，
  会删掉 `stateSeqNum > seqNum` 的 entry 实现“重放分叉就回退”。
- 恢复路径的“List”：checkpoint 里存的是 `UnionListState` 中的 `List<Object>` 个 marker，
  每个 marker 是 `Map<Integer,Long>`（Kafka partition→end offset，`getRecoveryMarker()` :312-330）。
  并行度 P 时每个 subtask 写 1 个 marker，UnionListState 广播 → 恢复时每个 subtask 拿到**全部 P 个 marker**。
  `rebuildState(List<Object>)`（:204-273）按 partition 取 `Math.min(offset)` 归并成 partitionMap，
  再 `consumer.assign` 所有 partition、`seek` 到 min offset、replay 到末尾，把每条 record `put` 回 `actionStates`。
  → 恢复完内存里**又是 Map**，且因 min-offset replay 扫了所有 partition，每个 subtask 的 Map 都含**全部 key**。
- 这直接解释了之前那条 orphan-state issue：rebuild 后 `subtask0 cache:{A,B}`、`subtask1 cache:{A,B}`；
  而 `notifyCheckpointComplete` 只按本 subtask keyed state 里的 `checkpointIdToSeqNums` 调 `pruneState`，
  外来 key 永不入表 → 残留。修复方向：rebuild 后只保留本 subtask key-group 负责的 key，或 prune 阶段对
  缓存全部 key 做“非本 subtask 负责即清”的清理（UnionListState 广播是固有语义，不能靠它隔离）。
- **性质澄清（用户追问关键点）**：这本质是**内存泄漏，不是正确性 bug**。
  (1) `actionStates` 缓存是**每 subtask 一个**（KafkaActionStateStore 每 operator subtask 各自 new），
      不是全局共享；正常运行时每 subtask 只缓存自己负责的 key，恢复后才被灌进全部 key。
  (2) `get()`（:151-194）**只读 `actionStates` 缓存、不回查 Kafka**，且按复合键隔离、divergence 检查只
      按 `key_seqNum_` 前缀过滤 → 外来 key 不干扰本 key 的读取/分叉判定，正确性无损；但缓存是 get 唯一来源，
      故恢复必须 replay 本 subtask 的 key，bug 仅在于把其他 subtask 的 key 也留下了。
  (3) 外来 key 永不进 `checkpointIdToSeqNums` → 不被 `pruneState` 触碰 → 本次 attempt 内永久常驻、
      不自愈；并行度越高/key 越多膨胀越夸张（每 subtask 多背总key−自己key 份）。
  (4) rescale 边界：恢复后若改并行度，key 所有权变化，缓存里旧归属的 key 仍不被清，错配持续（次要）。

## orphan-state 两条修复路径评估（用户提出：1.获取时只取当前key 2.清除时把其他也清掉）
- **关键前提已具备**：判断「某 key 是否本 subtask 的」有现成方法
  `OperatorStateManager.isKeyOwnedByCurrentSubtask(key, maxParallelism, range)`（:302-306），
  内部用 `KeyGroupRangeAssignment.assignToKeyGroup(key, maxParallelism)`（Flink 官方 key-group 语义）；
  range 由 `getCurrentSubtaskKeyGroupRange(maxParallelism, runtimeContext)`（:293-300）算，
  而 `getRuntimeContext()` 在 `initializeState` 的 `handleRecovery`（ActionExecutionOperator:496）即可用。
  缓存 key 的 part[0]=key.toString()，且 `ActionStateKeyPartitioner.partition()`(:40-42) 已要求 key 为 String，
  故 part[0] 即原 key，归属判定安全（若放开 String 约束会失效，需注意）。
- **路径1（获取时只取当前 key）**：rebuildState 改为只保留 marker offsets（不 replay），`get()` 由「仅缓存」
  改为「缓存未命中回查 Kafka」——seek 到该 key 所在 partition 的 marker offset，扫 partition 按 part[0] 过滤。
  内存最优（外来 key 永不进缓存），但改动 `get` 读路径（当前缓存-only）、需在 store 内留
  `Map<Integer,Long> recoveryOffsets`、并管理共享 consumer 的 seek，回归风险高。且 Kafka partition 含多 key
  （`murmurHash(part[0].hashCode())%numPartitions`，ActionStateKeyPartitioner:52），惰性 get 仍扫整 partition，I/O 省有限。
- **路径2（清除时把其他也清掉）【推荐】**：保留现有 bulk replay，恢复后按 key-group 过滤掉非本 subtask 的 key。
  最优子形态 2a：在 `rebuildState` replay 循环（KafkaActionStateStore:255-264）里按
  `isKeyOwnedByCurrentSubtask(part[0],...)` 跳过外来记录，外来 key 永不入缓存（避免峰值内存）。
  也可 2b：rebuildState 后加 `retainOwnedKeys(range)` 再清。读路径（`get` 缓存-only）完全不动，风险最低。
- **结论**：优先路径2-2a，复用现有归属判定、最低风险、直接消除内存泄漏；路径1 仅在还想省恢复 replay I/O
  时再考虑（且收益有限）。「清除」时机应在恢复后（handleRecovery 内 rebuildState 之后）一次性做，
  而非绑在每次 `notifyCheckpointComplete` 的 pruneState 上（外来 key 恢复后不再变，按 checkpoint 清是冗余）。
- **澄清（用户追问误区）**：「get 加 Kafka 回查」**仅路径1 独有**，路径2 的 get 完全不需要。
  原因：路径1 的 `rebuildState` 是 no-op、不 replay，恢复后 owned key 也未入内存，故首次 `get(ownedKey)`
  缓存 miss 时只能回查 Kafka；路径2 的 `rebuildState` 已把 owned key replay 进 `actionStates`，
  `get` 仍是缓存-only（:186 `actionStates.get`），无需回查。「从不进内存」是路径1 与 2a 共有目标，
  但 2a 在保留 bulk replay（I/O 位置不变）的前提下 skip 外来 key，**既拿到内存收益又不动读路径**，
  故 2a 严格优于路径1（路径1 把等量 I/O 从恢复挪到 get、并让 get 变 I/O 操作）。
